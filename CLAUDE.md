# CLAUDE.md

Repo-level guide for **Umbraco.Cms.Integrations** — a multi-package repository of official Umbraco CMS integration packages ("best of breed" / DXP initiative). Each package ships to NuGet and installs as an Umbraco backoffice extension.

This file is for **navigation, structure, and release workflow**. Package-specific detail lives in each package's `readme.md` / `docs/`.

---

## 1. Overview

- **What it is:** ~8 independent integration packages (CRM, commerce, search, SEO, automation), each versioned and released separately to NuGet.
- **Stack:** .NET (net10.0 on the v17/v18 lines), Umbraco CMS as the host, per-package **TypeScript + Vite** backoffice client compiled into `wwwroot`, built/packed via **Azure Pipelines**.
- **Not a single product:** there is no shared runtime library across packages — they are sibling projects that share only the repo, tooling, and release conventions.

## 2. Repository Structure

```
/src        - The integration packages (one .NET project per package)
/tests      - Test projects (sparse; not all packages have tests)
/examples   - Test sites (e.g. Umbraco.Cms.Integrations.Testsite.V18) for manual/local runs
/*.yml       - One Azure Pipeline per package: "azure-pipeline - <Name>.yml"

```

Each package under `src/` follows the same shape:
```
src/Umbraco.Cms.Integrations.<Area>.<Name>/
  <project>.csproj                     - .NET class library; <Version> drives the NuGet version
  Client/                              - TypeScript + Vite source
    src/, public/umbraco-package.json  - backoffice manifest (carries a version too)
    config.outputPath.js               - GENERATED by MSBuild before the client build (gitignored)
  wwwroot/                             - COMPILED client assets (committed) + umbraco-package.json
  readme.md, docs/, umbraco-marketplace-readme.md
```

## 3. Branching & Release Model

**One branch pair per Umbraco major.** For each supported Umbraco version there is a `main-v<N>` and a `v<N>/dev`:

- **`main-v<N>`** — reflects the **last released** state for that major.
- **`v<N>/dev`** — the **working branch**; always ahead of `main-v<N>` with unreleased work.
- **`main`** (no suffix) — the **legacy Umbraco 10–13** line.

**Flow:** work lands on `v<N>/dev` → a release is cut from dev → published to NuGet → dev is merged back into `main-v<N>` so `main-v<N>` matches what shipped. Do **not** commit release/working changes directly to `main-v<N>` — it re-diverges it from dev.

### Versioning is manual

There is **no `version.json` / GitVersion / Nerdbank**. Pipelines pack with `versioningScheme: off`, so the NuGet version comes straight from the csproj `<Version>`. When bumping a package, update **all three**:

1. `<project>.csproj` → `<Version>`
2. `Client/public/umbraco-package.json` → `"version"` (source)
3. `wwwroot/umbraco-package.json` → `"version"` (built copy)

Each package has **one major per Umbraco major** (e.g. Search.Algolia `6.x` = v17, `7.x` = v18; Crm.Hubspot `8.x` = v17, `9.x` = v18).

### Releasing (per package)

The build pipelines **only build + pack the `.nupkg` + SBOM as artifacts** — they do **not** push to NuGet or create tags. Publishing and tagging are separate/manual:

1. Bump versions on `v<N>/dev` (see above).
2. Build pipeline produces the artifact; **promote** that build to NuGet (separate release step).
3. Create an annotated git tag `release/<slug>-<version>` (e.g. `release/crm-hubspot-9.0.1`, `release/search-algolia-7.0.1`).
4. Create a GitHub release (title = tag name), linking the relevant PRs.
5. Merge `v<N>/dev` back into `main-v<N>`.

> Tagging/releasing is easy to forget — the v18 `.0.0` tags were missing entirely and had to be backfilled. Always do steps 3–5 after promoting.

## 4. CI Gotchas (Azure Pipelines)

- **Pipelines are per-package**, path-filtered to `src/<project>/**`, and trigger on both `main-v<N>` and `v<N>/dev`.
- **SBOM (cdxgen):** the cdxgen step fails unless `--spec-version 1.6` is pinned on the command. All active-line pipelines now have it; the legacy `main` line does not.
- **Committed `wwwroot` must match a fresh client build.** When `Client/src` changes, regenerate `wwwroot` (`npm install` + `npm run build`) or the .NET `StaticWebAssets` step fails referencing a stale chunk hash. The client build needs `Client/config.outputPath.js`, written by the `ClientAssetsBuildOutputPath` MSBuild target (`export const outputPath = '../wwwroot';`).
- **Compile-check .NET only** (skip the npm client build) with `-p:ShouldRunClientAssetsBuild=false`.
